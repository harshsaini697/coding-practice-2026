Frame the problem

The ledger is the source of truth. Optimize everything around it, but never trade away the invariant that money cannot be created, lost, or moved twice.

F

Functional

  • Internal and external transfers
  • Bill and merchant payments
  • Transaction status and history
  • Reversals, refunds, reconciliation
N

Non-functional

  • No double spend or duplicate debit
  • 99.99% API availability target
  • Complete, immutable audit trail
  • Predictable p99 under peak load
Interview move

Clarify whether transfers are within the bank or cross external rails. Internal transfers can be atomic; ACH, card, and wire flows are asynchronous workflows with pending and settled states.

01

Double-entry ledger

Every transfer writes equal debit and credit entries. Balances are projections of immutable ledger entries, not mutable truth.

02

Idempotent commands

A client-generated key has a unique database constraint. Retries return the original result instead of moving funds again.

03

Outbox events

Commit the ledger and event intent together. Publish asynchronously with at-least-once delivery and idempotent consumers.

03

Protect the money

Consistency model

Serialize only where financial invariants require it. Let everything else scale independently.

Must
Ledger writes

Serializable transaction or consensus-backed conditional writes.

Must
Balance checks

Read from the leader or use a locked versioned balance row.

Eventual
History & notifications

Materialized views may lag; expose a pending state to users.

Eventual
Analytics & reporting

Consume events asynchronously without adding ledger latency.

04

Stay up safely

High availability

Active-active compute.
Single-writer ownership.

Run stateless APIs across multiple zones and regions, but route each account shard to one consensus leader at a time. This avoids conflicting debits while preserving fast regional failover.

The honest trade-off

During a partition, fail closed for money movement.

Reads can remain available from safe snapshots, but a region without quorum must not accept ledger writes. “Pending” is better than an incorrect balance.

05

Push the design

Failure drills

Service crashes after commit, before response

The retry uses the same idempotency key, finds the durable transaction result, and returns success without posting new entries.

Message broker is unavailable

The ledger transaction still completes. The committed outbox record is retried until published; downstream consumers deduplicate by event ID.

Primary database node fails

The consensus group elects a leader from a quorum. Clients retry with bounded backoff. Transactions without a confirmed commit are safely replayed by idempotency key.

Two accounts live on different shards

Prefer co-locating common internal transfers. Otherwise use a durable workflow with holds, debit, credit, and compensation states rather than fragile distributed locking.
